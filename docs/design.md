# FTM design

Frazzer's Terminal Manager: a standalone terminal workspace manager for running many Claude Code agents (and plain shells) across repos and git worktrees, with a sidebar that shows which agent spawned which. Targets macOS and Linux.

## Concepts

- **Workspace**: one sidebar row. A folder (or a git worktree of a repo) plus its tabs and panes. Kind is `terminal` or `agent`.
- **Parent**: a workspace may have a parent. Agents spawned by a leader agent appear nested under it. Nesting depth is unbounded.
- **Tab / pane**: each workspace holds tabs; each tab is a split tree of panes; each pane is one PTY.
- **Status**: `starting | working | needs_input | idle | done`, driven by Claude Code hooks for agents.
- **Unseen**: a flag on the workspace, set when an agent finishes a turn (working or needs_input to idle or done) and cleared when it works again or the app shows it (`MarkSeen`). It lives in ftmd and is saved with the tree, so it survives app restarts and every client agrees.

## Architecture

```
ftmd (daemon)     owns PTYs, worktrees, workspace tree, Unix socket; keeps scrollback + terminal state
   ▲  Unix socket, newline-delimited JSON (ftm-core::protocol)
   ├── app        sidebar, tabs, panes, terminal rendering (UI choice below)
   └── ftm (CLI)  used by Claude skills, hooks, and scripts
```

Sessions survive both the app quitting and ftmd restarting or being upgraded: each pane's PTY lives in a small holder process (see PTY persistence), and workspace IDs stay stable across restarts.

Every PTY the daemon starts gets:

| Env var | Meaning |
|---|---|
| `FTM_SOCKET` | daemon socket path |
| `FTM_WORKSPACE_ID` | the workspace this pane belongs to |
| `FTM_PANE_ID` | the pane itself |
| `FTM_NAME` | the workspace's spawn name (`claude -n`); a later rename does not change it |
| `FTM_BIN` | absolute path of the `ftm` next to ftmd, for agents and skills when `ftm` is not on `PATH` |

Inherited `CLAUDECODE`, `CLAUDE_CODE_*` and `SUPACODE_*` are stripped, so an agent started from inside another agent is not treated as nested Claude Code. Panes run `$SHELL -l`; an agent's first pane runs `$SHELL -l -i -c '[/bin/sh -c "$FTM_SETUP"; ]claude [--settings <hooks>] [-n "$FTM_NAME"] ["$FTM_CLAUDE_ARG_1" ... "$FTM_CLAUDE_ARG_<n>" --] ${FTM_BRIEF:+"$FTM_BRIEF"}; exec "$SHELL" -l'`, with the setup, brief and extra arguments passed in the environment rather than interpolated. The extra arguments are `SpawnRequest.claude_args` (`ftm spawn agent ... -- <args>`), one variable per argument, so each reaches Claude as one argv entry and none is ever shell code. The `--` before the brief is only added with extra arguments, so an option taking several values (`--add-dir <dirs...>`, `--allowedTools`) cannot swallow the brief. `--resume <id>` with a brief resumes that session and sends the brief as its next prompt. ftmd refuses extra arguments for a terminal. Like the command, they live only in the first pane's environment: nothing re-runs the agent after a restart, since its pane keeps running in its holder. If that first pane exits while the workspace is still `starting` (the shell could not run the script, so neither the agent nor the fallback shell started), ftmd keeps the dead pane in its tab with its last output and a note, logs its screen, and sets the workspace `failed`; typing into it does nothing and closing it works as usual. A terminal spawned with `SpawnRequest.command` (the app's update pane; there is no CLI flag) runs `[/bin/sh -c "$FTM_SETUP"; ]/bin/sh -c "$FTM_COMMAND"; exec "$SHELL" -l` the same way, so the command is POSIX sh whatever the login shell and the pane stays open on a shell afterwards. ftmd refuses a command for an agent and does not add its cwd to the remembered folders. The command lives only in that first pane's environment, not in the saved tree, so a restarted or self-upgraded ftmd reattaches to the pane rather than running it again. `FTM_AGENT_CMD` (read by ftmd, default `claude`) replaces `claude` in that script, e.g. `claude --model haiku` or the fake agent the tests use; it is shell syntax, so it may carry quoted flags. Each pane keeps the last 1 MiB of raw output; `Subscribe` replays it, then streams live. The buffer is cut between escape sequences and UTF-8 characters (`crates/ftmd/src/trim.rs`), never inside one, since a replay starting in the middle of an image, title or link would print the rest as text; a sequence still being written when the cut comes (an image on its way) is kept whole, up to 32 MiB.

**Names.** A workspace shows its `title` (set by `ftm rename` or the sidebar) if it has one. An agent spawned with a name (`--name`, which the spawn skills always pass) runs as `claude -n <name>`, so `name` is its stable `SendMessage` address and is what it shows otherwise. An agent spawned without one (the `+` dialog's default) runs without `-n`; Claude Code then titles its terminal (OSC 0/2) "<status glyph> <task summary>", and ftmd takes the title of the pane the agent started in, drops the glyph (a spinner frame while working), ignores the placeholder "Claude Code" and a title equal to the name, and stores the rest as `auto_title`, shown until a rename. So unnamed agents name themselves without a tool call; their `SendMessage` address is then Claude's own default session name, not `FTM_NAME`. `name` never changes and is always `FTM_NAME` (for an unnamed workspace, the folder or branch). `ftm ls` prints `shown (name)` when they differ.

`ftm spawn` run inside a workspace defaults `--parent` to `$FTM_WORKSPACE_ID`. That is the whole leader/worker mechanism: no registration step, no config.

Socket location: `$XDG_RUNTIME_DIR/ftm/ftmd.sock` on Linux, `~/Library/Caches/ftm/ftmd.sock` on macOS. Unix socket paths are limited to ~104 bytes on macOS, so keep overrides short.

Everything a daemon keeps is keyed by its socket, so daemons on different sockets never share state: holder sockets in `<socket>.d/`, the saved tree in `$XDG_STATE_HOME/ftm/<socket path>.json`, hook settings in `<socket stem>.claude-settings.json` and the app-launched daemon's log in `<socket stem>.log`, all next to the socket. An installed FTM (`scripts/install.sh`) uses the default socket; `scripts/dev.sh` uses `ftmd-dev.sock` in the same dir and runs the app under the identifier `dev.frazzer.ftm.dev`, so the two run side by side with separate sessions, window state and web storage while sharing `~/.config/ftm` (settings, themes, sounds, repo setup). Panes get `FTM_SOCKET` for their own daemon, so `ftm` inside a pane, whichever binary, talks to the daemon that owns it.

## CLI

```
ftm ping                                      # "ftmd <version>", plus " (features: ...)" when ftmd reports any
ftm ls [--json]
ftm spawn terminal|agent [--path P] [--name N] [--worktree BRANCH [--base REF] [--copy-changes]]
                         [--brief FILE] [--parent ID | --detached] [--color NAME|#RRGGBB|random] [-- CLAUDE_ARGS...]
                                              # agent only: after -n, before the brief, e.g. -- --resume ID
ftm status working|needs-input|idle|done      # id from $FTM_WORKSPACE_ID
ftm close [--remove-worktree]
ftm rename NAME | --clear                     # display title only; "" also clears
ftm pin|unpin [ID]                            # sidebar's Pinned section; top-level workspaces only
ftm color <NAME|#RRGGBB|random>|--clear [--id ID]  # sidebar row color: red orange yellow green cyan blue purple pink gray
ftm move ID --parent PARENT_ID | --top-level  # reparent in the sidebar tree; nesting unpins, color is kept
ftm capture <pane|workspace> [--raw]          # screen + scrollback as text; --raw: last 1 MiB of output bytes
ftm send <pane|workspace> <text> [--enter]    # type into a pane; a workspace id means its first pane
ftm attach <pane|workspace>                   # this terminal shows the pane; Ctrl+] then d detaches
ftm show FILE [--id ID]                       # the app shows FILE in the workspace's viewer panel, without switching to it
ftm ask TITLE [--body TEXT | --body-file F|-] [--option ANSWER]... [--id ID]   # a decision for the user; prints its id
ftm flag TITLE [--body TEXT | --body-file F|-] [--id ID]                       # an FYI for the user; prints its id
ftm tasks [--json] [--all]                    # open tasks; --all adds answered, dismissed and resolved ones
ftm task done|rm TASK [--id ID]               # the agent resolves (done) or deletes (rm) one of its own tasks
ftm task answer TASK TEXT | dismiss TASK      # what the app's Tasks tab does; refused inside an agent workspace
ftm gc [--yes] [--no-fetch]                   # list merged FTM worktrees; --yes removes them and their branches
       [--include-upstream-deleted]           # also ones whose upstream was deleted (maybe closed unmerged); not with --no-fetch
```

Planned: `ftm tab`/`ftm split`.

## Worktree creation

Per-repo config at `~/.config/ftm/repos/<repo>.toml` (`$XDG_CONFIG_HOME/ftm/...` when set), plain files the app never holds in memory:

```toml
base = "origin/main"
setup = "direnv allow; rm -rf .venv; uv sync --all-extras"
copy_ignored_exclude = ["data", "*.parquet"]
```

`copy_ignored` picks which gitignored paths of the source checkout a new worktree gets:

| Value | Copies |
|---|---|
| unset or `true` (default) | every gitignored path, minus the built-in excludes and `copy_ignored_exclude` |
| `[".env", "profiles.yml"]` | only paths matching these globs (relative to the repo root); no excludes apply |
| `false` | nothing |

The built-in excludes (`DEFAULT_COPY_IGNORED_EXCLUDE` in `ftm-core/src/config.rs`) are `.venv`, `venv`, `node_modules`, `target`, `__pycache__`, `.pytest_cache`, `.ruff_cache`, `.mypy_cache`, `.tox` and `.DS_Store`: big or rebuildable, and in a Rust or Python checkout often gigabytes. `copy_ignored_exclude` adds to them, never replaces them. Each exclude is a name or glob matched against every component of a path, at any depth, and against the whole repo-relative path, so `node_modules` also skips `app/node_modules` and `data/*.csv` skips CSVs under `data/`.

Steps:

1. `git worktree add <wt> -b <branch> <base>`, or `git worktree add <wt> <branch>` for a branch that already exists. `<base>` is `--base`, else the repo config's `base`, else the remote's default branch: the current branch's upstream remote, else `origin`, and its default from `refs/remotes/<remote>/HEAD`, else `git ls-remote --symref`, else `<remote>/main` or `<remote>/master`. A repo with no remote starts from the source checkout's HEAD. A remote-tracking base (`origin/main`) is fetched first (`git fetch <remote> <branch>`, 60s at most, never prompting), so the branch starts from the remote's tip. If the fetch fails, ftmd logs a warning and uses the last fetch.
2. If `--copy-changes`: `git diff HEAD --binary | git -C <wt> apply` (staged + unstaged edits to tracked files)
3. If `--copy-changes`: copy `git ls-files --others --exclude-standard` (untracked, not ignored)
4. Always: copy gitignored paths as `copy_ignored` says (`git ls-files --others --ignored --exclude-standard --directory`, so an ignored directory is one entry). Files go through `fs::copy`, which on macOS clones on APFS (copy-on-write, near free) and falls back to a byte copy; modes are kept. Symlinks are recreated as symlinks and never followed, so a link out of the repo stays a link. A directory holding `.git` (a nested repo or worktree, e.g. `.claude/worktrees/*`) and special files are skipped. Copying is best effort: a path that cannot be read is logged as a warning and the rest still come over. ftmd logs each skipped path at debug and the totals at info.
5. Run `setup` in the first pane, then start `claude` (or the shell). Setup runs inline before the agent starts, so nothing has to wait on a sentinel file. It is POSIX sh whatever the login shell (it runs as `/bin/sh -c "$FTM_SETUP"`), so environment changes it makes do not reach the agent.

Worktrees live under `~/.local/share/ftm/worktrees/<repo>/<branch>` (`$XDG_DATA_HOME/ftm/worktrees` when set). `<repo>` names the repo a checkout belongs to, the same from every worktree of it (`ftm_core::repo`): the main checkout's directory when the common git dir is its `.git`, else the common git dir's, without a `.git` suffix (a bare repo, or one made with `--separate-git-dir`). `--remove-worktree` never forces: it fails on a dirty worktree, deletes the branch only if merged (`git branch -d`), and prunes empty `prefix/` directories.

## Worktree cleanup

`ftm gc` looks only at worktrees under the worktrees dir, so it never touches checkouts FTM did not make. The CLI runs the git checks itself and asks ftmd for the workspace tree, so ftmd must be running. It only knows about the ftmd on its socket, so a dev ftmd's workspaces are not seen by the installed `ftm`, and the other way round. For each repo it fetches the remote of `base` (by default the remote's default branch, found the way a new worktree's base is, else `origin/main`) without pruning, unless `--no-fetch` says to use the last fetch. Then it lists each worktree whose branch is done:

- **merged**: the branch tip is an ancestor of `base`. A branch with no commits of its own counts as merged.
- **squash-merged**: the branch's whole diff from where it left `base` matches a commit in `base` by patch id (`git cherry`).
- **upstream deleted**, only with `--include-upstream-deleted`: the remote branch is gone (per `git ls-remote`) and the branch tip equals the last fetched tip of its remote-tracking ref, so everything was pushed. This catches PRs merged in a way the two checks above miss, such as a rebase merge. It cannot tell such a PR from one that was closed unmerged, whose commits would then survive only in the reflog, so without the flag these worktrees are skipped with a reason naming it. Seeing the deletion needs the fetch, so the flag conflicts with `--no-fetch`.

A done worktree is skipped, with the reason printed, when any of these hold:

- a workspace's cwd is in it
- `git status --porcelain` shows changes (uncommitted, or untracked and not ignored)
- its upstream was deleted but it has commits since the last fetched tip
- its upstream was already pruned, so what was pushed is unknown

Commits whose changes are not in `base` keep a branch out of the merged and squash-merged sets, so nothing unpushed is lost there.

Without `--yes`, gc only lists. With `--yes`, it runs:

1. `git worktree remove` (never forced; ignored files go with the worktree)
2. `git branch -D` (squash merges are not ancestors, so `-d` would refuse)
3. deletes the stale remote-tracking ref of an upstream-deleted branch
4. prunes empty `prefix/` directories
5. `git worktree prune` per repo

A worktree whose removal fails, or whose branch or tracking ref could not be deleted after it, is reported on stderr and makes gc exit non-zero.

Detached worktrees and unmerged branches are not listed.

## Testing

- `cargo test` runs `crates/ftmd/tests/agents.rs`: ftmd on a private socket with temp `HOME`/`XDG_*` and `FTM_AGENT_CMD` set to a fake agent that drives the real `ftm` CLI (nesting, `--detached`, status, worktree copy + setup, close/reparent/kill, worktree removal); `crates/ftmd/tests/gc.rs` runs `ftm gc` against a repo with a bare origin. `tasks_reach_the_agent_that_posted_them` in `agents.rs` posts tasks from a fake agent that records the bytes typed into its pane, with and without bracketed paste, and covers withdrawing, refusals, the restart and closing.
- `scripts/agent-smoke.sh` is an opt-in live check with real Claude (Haiku): an isolated ftmd, a leader agent that spawns a child, and assertions on its results file, `ftm ls --json` and `ftm capture`. It costs a little usage, so it is not part of `cargo test`. Hook-driven status checks get added with milestone 5.

## Claude Code integration

ftmd writes hook settings to `<socket stem>.claude-settings.json` next to its socket (`ftmd.claude-settings.json` for the default one) and starts every agent with `claude --settings <that file>`, so the user's own `~/.claude/settings.json` is untouched (hook entries from both apply). Each hook runs `<ftm next to ftmd> status <s> >/dev/null 2>&1 || true` with a 5s timeout: silent (a `UserPromptSubmit` hook's stdout would be fed to Claude), never failing, and a no-op outside FTM.

| Hook (matcher) | Status |
|---|---|
| `UserPromptSubmit`, `PostToolUse` | `working` |
| `PermissionRequest` (fires as soon as a tool needs approval) | `needs_input` |
| `PreToolUse` (`AskUserQuestion`) | `needs_input` |
| `Notification` (`permission_prompt\|elicitation_dialog\|elicitation_url_dialog`) | `needs_input` |
| `Stop`, `StopFailure` | `idle` (`Stop` runs `ftm status idle --hook`, which reads the hook input for the background subagents still running) |
| `SessionEnd` | `done` (best effort: a killed session may not send it) |

The 60s `idle_prompt` notification is deliberately not mapped, so a finished agent never turns red. `PostToolUse` rather than `PreToolUse` marks work so it cannot race the `AskUserQuestion` hook, and it clears `needs_input` once a prompt is answered. In the app, agent rows show a dot (starting blue, working green, needs input red, idle grey, done hollow grey, failed hollow red, finished but unseen yellow; CSS variables `--status-*`, taken from the theme's palette and nudged until they read against the sidebar); terminals show none. `ftm ls` marks unseen workspaces `(unseen)`.

`needs_input` also raises a desktop notification (agent name, "needs input"), plays the needs-input sound, and badges every ancestor row with the count of agents below it that need input. A workspace turning unseen plays the finished sound, unless it is the selected workspace and the window has focus: then the app marks it seen at once and stays quiet. Each background subagent's hand-back starts another turn, so an agent that fans out plays the finished sound once per hand-back; with `[sounds] wait_for_subagents` the app stays quiet while `background_agents` (running subagents from `Stop`'s `background_tasks`, shells left out since they can run for good) is nonzero, and holds the sound 1.5s so a second hand-back queued behind the first can cancel it. Selecting an unseen workspace (or focusing the window on one) marks it seen. A session ending after the agent was already idle does not count as finishing again. Agents are started with `claude -n <name> "<brief>"`, so `SendMessage` between leader and workers keeps working as today. `sonarx:spawn-repo-agent` and `sonarx:agent-shutdown` switch from `supacode ...` to `ftm spawn` / `ftm close`.

## Settings

The app's settings live in `~/.config/ftm/config.toml` (`$XDG_CONFIG_HOME/ftm/...` when set) and are edited from the sidebar's ⚙; Save rewrites only the keys the app owns, Cancel reverts any live preview.

```toml
[terminal]
font_family = "Menlo"
font_size = 13
ligatures = false
line_height = 1.0
option_as_meta = "both"  # macOS Option keys that send Meta: "left", "right" or "off" to type ∫ ƒ é with them
app_scroll = "rows"      # wheel in full-screen apps: a step per row of travel, or "xterm" for xterm.js's coarser steps

[theme]
name = "Supacode Dark"   # or follow_system = true with dark/light

[sounds]
needs_input = "Clink"    # a name from the sound list; "" plays nothing
completed = "Done"
volume = 0.7             # 0 to 1
wait_for_subagents = false  # true: no finished sound while the agent still has background subagents running

[notifications]
enabled = true           # desktop notifications for an agent needing input and a new task

[tasks]
enabled = true           # the task inbox: agents are told about ftm ask/flag, the commands work, the Tasks tab shows

[updates]
check = false            # look for a newer release; unset means on, except in a dev build
channel = "nightly"      # or "stable"; unset means this build's own
```

`[updates]` keys are left out while unset, so Save removes one set back to automatic (and the section if that empties it).

Themes are Ghostty theme files: built in, in `~/.config/ftm/themes`, or found in Ghostty's and Supacode's theme folders. Sounds come from the app's built-ins (`app/src-tauri/sounds`, synthesized by `scripts/gen-sounds.py`), `~/.config/ftm/sounds` (wav, aiff, ogg/oga, mp3, m4a, caf, flac; named by file stem), macOS `/System/Library/Sounds` and freedesktop `/usr/share/sounds/freedesktop/stereo`; on a name clash yours win over built-ins over the system's. The webview decodes and plays them with Web Audio (the bytes come over IPC), never a media element, so FTM never becomes the system's Now Playing app and never takes the media keys. WKWebView decodes every listed format; WebKitGTK decodes what its GStreamer plugins handle, and a sound it cannot decode is logged and plays nothing. Picking a sound in the dropdown plays it; ▶ replays it.

## UI

Sidebar with a `+` button: pick terminal or agent, pick a folder; if it is a git repo, optionally tick "worktree" and enter a branch (plus "copy my changes"). Rows nest by parent and show status, branch, and PR link. Right-click a row (or double-click its name) to rename it inline: Enter saves, Esc cancels, an empty name goes back to the spawn name. A rename sets the workspace's `title`, which is shown instead of `name`; `name` stays as spawned because it is `FTM_NAME` for every pane opened later and the agent's Claude session name (the `SendMessage` address). `ftm ls` prints `title (name)` when they differ. Right-click a top-level row (or `ftm pin`/`ftm unpin`) to move it in or out of the Pinned section; a child stays under its parent while that parent exists, so ftmd refuses to pin it, and `ftm ls` marks pinned workspaces `(pinned)`. `ftm move ID --parent PARENT_ID` nests a workspace under another and `ftm move ID --top-level` takes it out (`Request::Move`); its children go with it. ftmd refuses an unknown id and a move under the workspace itself or one of its descendants, which would make a cycle. Moving only changes where the row sits, not the workspace: its name, panes, worktree and color stay as they are (the nudged child color is only picked at spawn). Nesting a pinned workspace unpins it, since pins are top-level only; moving it back out leaves it unpinned. The app needs nothing new for it: every change sends the whole tree as a `Workspaces` event and the sidebar rebuilds its rows from each workspace's `parent`. The CLI refuses `move` when ftmd lacks the `move` feature, since an older ftmd answers an unknown request with a parse error rather than a reason. Right-click a row's Color… (or `ftm color`) to give it a color, shown as a stripe on its left edge over a faint tint; nested workspaces can have their own. Color… → Custom… opens the system color picker, starting from the row's current color, and sets the `#rrggbb` it closes on. `random` (Color… → Random, `ftm color random`, `--color random`) is resolved by ftmd to a `#rrggbb` with saturation and lightness in a band that reads on light and dark themes; only the hex is stored. `ftm spawn --color` creates the workspace already colored: `SpawnRequest.color` sets it with the rest of the workspace, and the CLI refuses it when ftmd lacks the `spawn_color` feature rather than have an older ftmd drop it. A child spawned without a color under a colored parent starts with the parent's color nudged in hue and lightness (`ftm_core::color::child_color`), one none of its siblings has; recoloring the parent later leaves children alone, and an uncolored parent gives uncolored children. ftmd needs the palette's values for that, so `WORKSPACE_PALETTE` is also in `ftm-core`'s `model.rs`, with a test that keeps it the same as the app's. The app's spawns are all top level, so they color from the folder instead: the `+` dialog's Color row defaults to Auto, and a folder row's + menu always uses it, which is the folder's own color (right-click a folder → Color…: Use global setting, None, a palette color, Random or Custom…; `SetFolderColor`, stored in `Folder.color`, feature `folder_colors`, shown as a dot before the folder's name), else `[workspaces] folder_color` in `config.toml` (Settings → Workspaces), else none. The app sends the result as `SpawnRequest.color`, `random` included, so each spawn gets its own. Overall: an explicit color, then the parent's nudged color, then folder, then setting. Palette names map to fixed colors (`WORKSPACE_PALETTE` in `app/src/colors.ts`), the same on every theme so each name looks like itself, and `#rrggbb` is used as given; `SetColor` stores it in the workspace's `color`, and `ftm ls` prints `(color <name>)`. Drag a row in the Folders section to rearrange it (`ReorderFolders`); ftmd saves that order apart from the most-recently-used order the `+` dialog's recents use. New folders go to the end, and a state file from before the order existed starts sorted by name. Drag the sidebar's right edge to resize it, between 180px and half the window; double-click the edge to go back to 264px. The width is the app's alone, kept in the webview's `localStorage` like the collapsed sections, so ftmd never sees it. Workspace rows drag the same way among the rows under the same parent in their section (`ReorderWorkspaces`): ftmd saves one workspace order, which `ftm ls` and every `Workspaces` event follow, so an app from before the order still shows it. New workspaces go to the end, and a state file from before the order starts sorted by the name the sidebar shows. Each section's header has a sort button (shown on hover, and always while the section is off its default): Name, Manual (the dragged order) or Color (palette order, then `#rrggbb` colors, then rows without one; ties keep the manual order). Workspace sections start sorted by Name; Folders offers Manual and Name and starts in Manual, its dragged order. Children under a parent sort the same way as the parent's section, and rows only drag in manual order. The choice is the app's alone, kept in the webview's `localStorage` like the collapsed sections. Each workspace has tabs; each tab splits into panes.

Must run on macOS and Linux as a standalone desktop app (never inside a browser).

**Decision: Tauri v2 + xterm.js.** Tauri renders in the OS webview (WKWebView on macOS, WebKitGTK on Linux) inside its own native window. gpui stays the fallback if xterm.js rendering or webview quirks become a problem.

| Option | Terminal | Notes |
|---|---|---|
| **Tauri v2 + xterm.js** (chosen) | xterm.js WebGL | Rust backend, TS frontend. Proven for TUIs (VS Code). Fastest path to the full sidebar/tabs/splits UI. |
| gpui + alacritty_terminal | alacritty_terminal grid, GPU rendered | All Rust, native feel. Zed's terminal panel is the reference. gpui's API is young and thinly documented. |
| libghostty | Ghostty | Ghostty's own frontends are Swift (macOS) and GTK (Linux): two UIs to build. Not worth it for a cross-platform app. |

The daemon/CLI are independent of this choice; the app is just another socket client plus a PTY stream consumer.

**Keyboard.** Pane keys go through xterm.js, with a custom key handler (`app/src/keys.ts`) in front. It implements the kitty keyboard protocol (`app/src/kitty.ts`) because xterm.js 6.0 lacks it; 6.1 adds it as `vtExtensions.kittyKeyboard`, which can replace the module once 6.1 is stable. Only the "disambiguate" and "report alternate keys" flags are supported, and a `CSI ? u` query reports just those; each screen has its own flags and stack, and the alternate screen's are cleared when it is entered. Claude Code and fish both turn it on, so Shift+Enter reaches them as `CSI 13;2u`. Without the protocol, Shift+Enter sends `ESC CR`, as Claude Code's `/terminal-setup` makes iTerm2 send. A replay of the daemon's buffer (`reset: true`) gets no query replies, since the program asked long ago; the flags it pushed are rebuilt from the replay, so a program whose push has scrolled out of the last 1 MiB falls back to legacy keys until it pushes again. On Linux, Ctrl+Shift+C copies the selection (nothing without one), and Ctrl+Shift+V and Shift+Insert paste through `term.paste`, so bracketed paste applies; both go through `tauri-plugin-clipboard-manager`, since WebKitGTK refuses `navigator.clipboard` outside a gesture and asks for confirmation within one. macOS keeps Cmd+C/V from its Edit menu. Without the protocol, Linux Ctrl+Backspace sends `^W` and Ctrl+Delete `ESC d` (xterm's `^H` and `\e[3;5~` are unbound in bash's readline); Ctrl+arrows keep xterm's `\e[1;5D`/`\e[1;5C`, which distro inputrcs, fish, zsh and editors bind, and Alt+Backspace is already `ESC DEL`. With it on, they get the protocol's encoding. macOS has iTerm2's "Natural Text Editing" instead: Option/Cmd+arrows and Option/Cmd+Backspace send the emacs keys, protocol or not. Option is Meta by default (xterm's `macOptionIsMeta`, set per keydown from which Option keys are down, since `[terminal] option_as_meta` can pick one side); a composing Option is not a modifier under the protocol either. Linux Alt+key already sends `ESC` + key.

**Wheel.** The main screen scrolls its own scrollback through xterm.js. A program that reads the mouse, or runs on the alternate screen without it (Claude Code's fullscreen mode, vim, tmux, less), gets the wheel as SGR reports or arrow keys instead, and there xterm.js 6.0 sends at most one per wheel event, after damping events under 50px to 30%, so a light trackpad swipe barely moves it and a mouse wheel crawls. Native terminals send one per row scrolled, and programs tune their scroll speed to that (Claude Code scrolls a line per report unless it detects VS Code). With `[terminal] app_scroll = "rows"` (the default) a custom wheel handler (`app/src/wheel.ts`) does the same, carrying fractions of a row to the next event in the same direction. It tracks the SGR encoding (DECSET 1006) itself; a program on another encoding, Shift+wheel and the main screen keep xterm.js's handling, and `"xterm"` keeps it everywhere.

**Links.** Cmd+click (macOS) or Ctrl+click (Linux) opens a link in a pane; a plain click still selects or reaches a TUI that tracks the mouse. Plain-text URLs come from `@xterm/addon-web-links`, which joins soft-wrapped rows, and OSC 8 hyperlinks from the terminal's `linkHandler`, whose hover puts the target in the pane's tooltip. Both go through `openableUrl` (`app/src/links.ts`) and then the `open_url` command (`app/src-tauri/src/links.rs`), which each allow only `http`, `https` and `mailto` and pass the URL as one argument to `open` or `xdg-open`; `file:` and other apps' schemes never reach the OS. Claude Code emits OSC 8 only for terminals it recognizes by `TERM_PROGRAM` and the like, which FTM does not fake, or with `FORCE_HYPERLINK` set. `supports-hyperlinks`, which it and many npm (and the Rust crate's) CLIs use, honours `FORCE_HYPERLINK` before checking for a TTY, so a pane-wide setting would put escape codes into pipes, log files and the Bash tool's results. Instead the hook settings agents get with `--settings` (`crates/ftmd/src/hooks.rs`) set it in their `env`, and a SessionStart hook (every source: startup, resume, clear, compact) appends `unset FORCE_HYPERLINK` to `$CLAUDE_ENV_FILE`, which Claude Code sources before each Bash command; with no `$CLAUDE_ENV_FILE` the hook does nothing. Settings `env` overrides an inherited value, so an agent's Claude Code gets links even with `FORCE_HYPERLINK=0` in the user's shell; there is no settings-level "only if unset", and the launch line has to stay valid in fish, zsh and bash and keep `FTM_AGENT_CMD` and a user's `claude` alias working. Claude Code hard-wraps a long URL with cursor moves, not soft wraps, and repeats its OSC 8 link with the full target on every row, so clicking any row opens the whole URL. A `claude` started by hand in a terminal pane gets no `--settings`, so it prints plain text: a URL that fits on a row opens, but for a hard-wrapped one only the first row is a link, cut off at the row's end. `export FORCE_HYPERLINK=1` in a shell rc turns its links on too, at the cost of escape codes in that shell's piped output.

**Viewer.** A Cmd/Ctrl+click on a file opens it in the workspace's viewer panel when FTM renders it (markdown, HTML, images, video: `artifactKind` in `app/src/artifacts.ts`) and in VS Code otherwise (the `open_file` command, `vscode://file/<path>:<line>` on macOS and `code -g` on Linux, with the line when the text had `:line`). Files arrive as OSC 8 `file:` links (only for this machine: no host or `localhost`), which agents' Claude Code prints for the files it reads and writes, and as paths printed as plain text (`docs/plan.md`, `src/a.rs:12`), resolved against the workspace folder and linked only when they name an existing file. The panel sits right of the panes, one per workspace: each remembers its file, whether it is collapsed and its last ten files, in `localStorage` (`ftm.viewer`), so ftmd and older apps see nothing of it. Collapsed, it is a strip with the file's name; Cmd+B (Ctrl+Shift+B on Linux) or the strip expands it, and the left edge resizes it (`ftm.viewerWidth`). Collapsing or leaving a video unloads it, since a media element holds the media keys. While the panel is open and the window visible, the file is checked every second (`artifact_stat`, size and mtime) and redrawn when it changes, at the same scroll position. Files are read whole through `read_artifact` (`app/src-tauri/src/artifacts.rs`): absolute paths to regular files only, after resolving symlinks, at most 512 MiB. Pane output decides which paths get read, so nothing it names runs with the app's rights: the main window has no CSP and its commands are not capability-gated, so a document is never put in the app's DOM. Markdown is rendered with `marked`, sanitized with DOMPurify, its local images inlined as `data:` URLs, and shown in an `<iframe sandbox="allow-scripts">` whose CSP lets only the viewer's own script run (by nonce); that script reports link clicks (web links go to `open_url`, relative ones are opened like a click on a path) and the scroll position to the panel by `postMessage`. HTML runs its own scripts in the same kind of frame, with a CSP `<meta>` put before anything but its doctype that blocks every fetch, and `<base target="_blank">` so a link asks for a new window, which the sandbox refuses, instead of loading a page into the panel. Both frames have an opaque origin: Tauri injects its IPC into the main frame only and refuses a request whose Origin is `null`, and the frame cannot reach the app's DOM. Images and video are shown from Blob URLs in the panel itself.

`ftm show FILE` (`Request::Show`, feature `show`) is how an agent puts a plan, report or screenshot in front of the user. The CLI resolves the file and checks it exists; ftmd checks the workspace and broadcasts `Event::Show` to subscribed apps, keeping nothing, so a show while no app runs is lost. The app opens the file in that workspace's panel (expanding it if collapsed) without selecting the workspace or taking keyboard focus. Shown in a workspace that is not on screen, it marks that workspace's sidebar row with ◧ until the workspace is looked at. A file FTM does not render shows as a note with the VS Code button. An older app parses the event as `Event::Unknown` and ignores it.

**Tasks.** An agent that needs the user posts a task instead of waiting in its pane: `ftm ask` for a decision it is blocked on, `ftm flag` for something the user should know (feature `tasks`; the CLI refuses every task command when ftmd lacks it, since an older ftmd answers an unknown request with a parse error rather than a reason). A task (`ftm_core::task::Task`) has a number (`id`, from 1 per daemon, short enough to type), the posting `workspace` (`$FTM_WORKSPACE_ID`, or `--id`), `kind` (`decision` or `flag`), a one-line `title` (control characters dropped, whitespace runs made one space, at most 200 characters), an optional markdown `body`, suggested answers (`options`), `created_at`, and a `state`: `open`, `answered` (with the `answer`), `dismissed` by the user, or `resolved` by the agent (`ftm task done`). ftmd keeps tasks in the saved tree (`tasks` and `next_task`, so numbers are not reused after a restart), drops a workspace's tasks when it closes, keeps at most 200 that are no longer open, and sends the whole list as `Event::Tasks` on subscribe and after each change. `ResolveTask` and `RemoveTask` carry the caller's workspace and are refused for another workspace's task, so an agent only withdraws its own. `ftm task answer` and `ftm task dismiss` refuse to run when `$FTM_WORKSPACE_ID` names an agent workspace, so an agent cannot approve its own question by mistake; it is not a security boundary, since `ftm send` can type anything.

`[tasks] enabled` (Settings → Workspaces, on by default) turns the inbox on and off. The hook settings ftmd gives agents run `ftm hook session-start` on `SessionStart` for the `startup` and `clear` sources (a fresh conversation; `resume` and `compact` already hold it, and the command checks the source again). It reads `config.toml` when it runs, so a change reaches the next agent without restarting ftmd, and prints `AGENT_GUIDE` (`ftm_core::task`) as `hookSpecificOutput.additionalContext`: the commands, "post, then end your turn", the exact reply formats, and routing (technical and design questions to the leader over `SendMessage`; `ftm ask` only for what only the user can decide, since approvals relayed over `SendMessage` get refused; leaders do not re-ask; never answer or dismiss a task yourself; `ftm task done` once settled). It prints nothing when tasks are off, and never fails. Off, `ftm ask` and `ftm flag` refuse ("tasks are off in FTM settings"), and the app hides the Tasks tab and badges and raises nothing for new tasks; ftmd keeps any tasks it has, and they come back when the setting does. An answer reaches the agent typed into its pane, so Claude Code takes it as a prompt from the user, the same as keyboard input (`UserPromptSubmit` fires), not as a message from another session.

`ftm tasks --json` is a stable shape for watchers: an array of objects that always have every key, `null` when unset:

| Key | Value |
|---|---|
| `id` | the task number |
| `workspace` | the posting workspace's id |
| `agent_name`, `agent_spawn_name` | its shown name (`title`, else `auto_title`, else `name`) and its spawn `name` |
| `kind` | `decision` or `flag` |
| `title`, `body`, `options` | as posted (`options` is `[]` without any) |
| `created_at`, `closed_at` | Unix seconds; `closed_at` is `null` while open |
| `state` | `open`, `answered`, `dismissed` (by the user) or `resolved` (withdrawn by the agent) |
| `answer` | the answer typed into the agent's pane, for `answered` |

Without `--all` only `open` tasks are listed. A task deleted with `ftm task rm`, or dropped with its workspace, is gone from the list.

Answering (`AnswerTask`, from the app or `ftm task answer`) types the reply into the agent's pane, then marks the task answered. The message stands on its own in the agent's transcript (`ftm_core::task::reply_message`):

```
[FTM task #7 answered] Q: <title> — A: <answer>        a decision
[FTM task #7 reply] FYI: <title> — A: <answer>         a flag
```

A multi-line answer starts on the line after `A:`. The text goes in as one bracketed paste, then Enter in a separate write 150ms later: Claude Code keeps the paste's newlines without submitting at each one, shows the whole text in its transcript (checked with 30 lines), and takes the Enter as submit; while the agent is mid-turn it holds the prompt in its input box and submits it when the turn ends. The pane goes to the agent's startup pane (`agent_pane`, else the first tab's first pane). A program that has not turned on bracketed paste (DECSET 2004, read from ftmd's emulator) gets the reply flattened onto one line, so no newline submits half of it. Control characters other than newline and tab are dropped from the title and answer, so nothing in them can end the paste early and be read as keys. ftmd refuses, leaving the task open, when the task is no longer open (answered, dismissed, or withdrawn by the agent meanwhile), the workspace is not an agent, the agent is `needs_input` (a permission prompt or question dialog would take the text as keys), its session ended (`done` or `failed`: the pane is a shell now), or it has no live pane. The app shows the reason under the task.

The app shows tasks in a Tasks tab of the viewer panel, next to the file tab. Tasks are global: every agent's open tasks, grouped under the agent's shown name with its color stripe and status dot, in sidebar order, whichever workspace is selected. Clicking a group's header selects that agent's workspace and keeps the Tasks tab on screen there. Each task shows a kind icon, its title, its body behind ▸ (markdown through `marked` and DOMPurify, kept to text formatting: no images, media, forms, styles or attributes beyond a link's target, since unlike the viewer's documents it sits in the app's own DOM; links go through `open_url`), its options as buttons that send that answer, and a reply box (Enter sends, Shift+Enter adds a line); flags have Dismiss, decisions a × on hover. The tab redraws only when what it shows changes, and a tree update does not pull keyboard focus from a reply being typed back to the pane. A workspace without a file shows the panel only while there are open tasks, collapsed or expanded by one flag shared by all such workspaces (`localStorage` `ftm.tasksCollapsed`, collapsed by default); a workspace with a file remembers which tab it shows (`Entry.tab` in `ftm.viewer`), and a new file shown there switches it back to the file tab. Collapsed, the panel's strip carries the open count (red while a decision waits; clicking it opens Tasks), as does the Tasks tab, and each agent's sidebar row shows how many of its tasks are open. A new task never expands the panel or switches its tab, since either would resize or cover what the user is reading; a new decision raises a desktop notification (unless `[notifications] enabled` is off, Settings → Alerts, which also silences the needs-input notification; sounds have their own settings, so a test instance with empty sound names and notifications off is silent) ("<agent> asks", the title) and plays the needs-input sound, a flag only the notification ("<agent> flagged"). The tasks replayed on (re)subscribe raise nothing. Cmd+B (Ctrl+Shift+B) collapses and expands the panel whichever tab it shows.

**Images.** Panes draw sixel and iTerm2 inline images (`OSC 1337;File=`) with `@xterm/addon-image`, so `imgcat`, chafa, timg and viu work. The addon reads only the single-sequence form, while current `imgcat` sends iTerm2 3.5's multipart form (`MultipartFile=`, `FilePart=` chunks, `FileEnd`), so each pane's output goes through `MultipartImages` (`app/src/iterm.ts`) first, which joins those into one `File=` sequence, carrying a sequence split between reads over to the next. The addon adds sixel to the DA1 reply, answers XTSMGRAPHICS and reports the window and cell size in pixels (CSI 14t/16t), since ftmd's terminals report 0 pixels. Kitty's graphics protocol is not there: the addon only has it in a beta. Claude Code draws no images in FTM either way: it waits for an XTVERSION reply naming kitty, ghostty or iTerm2, and its kitty images use Unicode placeholders. A replay draws a pane's images again, and the addon keeps every copy until its storage fills, so each pane gets 16 MB (the addon's default is 128 MB) and images up to 8M pixels. XTSMGRAPHICS replies are query replies to the replay filter. Images reach a replay only while they are in the last 1 MiB of output, so a big one pushes the text before it out of the redraw (the text stays in `ftm capture`).

**File drops.** Tauri's native drag-drop handler takes OS file drops before the webview sees them (which is also why the folder drag uses pointer events), so the app listens with `onDragDropEvent`. The pane under the drag is outlined, and a drop pastes the paths there through `term.paste` (`app/src/drop.ts`): each one is a POSIX shell word, as is when it holds only `[A-Za-z0-9_@%+=:,./-]` and single-quoted otherwise, joined by spaces with one after the last. A drop outside a pane does nothing. The event's position is typed `PhysicalPosition`, but wry reports GTK widget and AppKit view coordinates, which are CSS pixels, so it goes to `elementFromPoint` unscaled; only Windows, which FTM does not ship, reports physical pixels.

## PTY persistence

Each pane runs under a holder: `ftmd pty-holder`, the same binary in a hidden mode, started in its own session so nothing aimed at ftmd (a signal to its process group, its terminal closing) reaches it. The holder owns the PTY master and the pane's process tree, keeps the last 1 MiB of output, and serves one ftmd at a time on `<ftmd socket>.d/<first 12 hex digits of the pane id>.sock` (short enough for macOS's 104 byte socket path limit; ftmd also finds holders from 0.1.8 and earlier on `<pane>.sock`) with length-prefixed frames (`crates/ftmd/src/frame.rs`): `Hello{version, rows, cols}` then the whole buffer then live output to ftmd; `Input`, `Resize` and `Kill` back. A new connection replaces the old one, which is how a restarted ftmd takes over. The holder writes input to the PTY on its own thread, so a program that stops reading its input never keeps a `Resize` or `Kill` from landing, and ftmd queues each pane's frames on a thread of its own, never writing to a holder under its state lock. A holder that cannot write output to ftmd for 5s hangs up on it (it may have sent half a frame) and keeps buffering; ftmd reconnects and redraws the pane from the buffer, and takes a pane for gone only once its holder's socket is. Frames that fail to go out meanwhile wait in the pane's queue for the new connection, and after reconnecting ftmd sends the size clients last asked for if the holder's `Hello` reports another. A holder whose processes are gone before any ftmd has connected (a startup command that fails at once) keeps its socket and output for up to 5s, so ftmd still gets them. On `Kill` the holder hangs up the shell's process group and the terminal's foreground group (an agent run by an interactive shell has its own group and ignores SIGHUP), SIGKILLs what is left after 2s (every process group still in the pane's session, from `/proc` on Linux and `proc_listallpids` on macOS, so a job that ignores SIGHUP does not outlive the shell), and exits once the terminal is empty, or 2s later regardless, removing its socket; ftmd waits for that before `--remove-worktree` deletes anything. ftmd sends a closed pane's `Kill` both on the pane's connection and on a new connection of its own, which it reads until the holder exits: the pane's connection may be one the holder already hung up on. A reconnect that finds its pane closed sends `Kill` too, since its connection may have replaced that one.

ftmd keeps its own copy of each pane's output and feeds it through a headless `vt100` emulator, so `ftm capture` reads the screen and scrollback as text, `ftm attach` starts with a redraw of the current screen (it sizes the pane to its terminal, and when the last attach ends ftmd puts back the size the pane had before, or the latest another client set meanwhile), and `Subscribe` replays raw output to the app. It saves the workspace tree (workspaces, tabs, layouts, statuses) to `$XDG_STATE_HOME/ftm/<socket path>.json` (`~/.local/state/ftm/...`) 250ms after a change, on a thread of its own and off the state lock, so a burst of changes (a status per tool use of every agent) is one write; a `SetStatus` that changes nothing is neither broadcast nor saved. SIGTERM and a hand-over save at once. The file is keyed by socket so a dev or test daemon never picks up another daemon's panes, and is removed when the tree is empty. Each save is synced before it is renamed into place; a state file that does not parse is moved to `<file>.bad-<unix time>` with an error in the log, and ftmd starts empty (a hand-over still refuses one). On start it reloads the tree, reconnects to each pane's holder and rebuilds its screen from the holder's buffer. A pane whose holder is gone (its processes exited while ftmd was down, or the machine rebooted) is dropped from its layout; the workspace stays, possibly without tabs. Nothing is restarted after a reboot. Stopping ftmd (SIGTERM) leaves every pane running; closing a pane or workspace is what kills it.

The app is just a client: quitting it changes nothing, and on launch it starts ftmd if needed, then restores its window geometry (`tauri-plugin-window-state`) and the selected workspace and tabs (`localStorage`).

**Upgrading.** `scripts/install.sh`, `scripts/dev.sh` (each on its own socket) or any SIGTERM restarts ftmd on new code without touching panes, but each holder keeps running the binary it was started from until its pane closes; new panes get the new holder. ftmd and holders agree on `frame::VERSION`: a change to the frames bumps it, and a newer ftmd then cannot reattach older holders (it logs `pane holder speaks version N`, drops those panes from the layout and leaves their processes running unattached), so close panes before upgrading across a version bump. The frame protocol is still version 1.

ftmd also upgrades itself (`crates/ftmd/src/upgrade.rs`). It polls the file it was started from (resolved at startup, so a dev ftmd watches `target/debug/ftmd` and a nightly one its own bundle) every 2s for a new inode, size or mtime, and acts once the file has held still for 2s. It runs the new file with `--handshake`, which prints `{"version", "frame", "channel"}`. If that fails, or the frame version differs, it stays put and sends `UpdateBlocked` (replayed on every subscribe), which the app shows as a notice: switching would lose every pane. It also stays put, with an `UpdateBlocked` saying why, when the channel differs (`stable` or `nightly`, from `FTM_CHANNEL`). On Linux the two channels' packages replace each other at the same `/usr/bin` path, and the other channel's ftmd belongs on its own socket, so the old ftmd keeps its panes until it exits and the new channel starts a daemon of its own. A build without `channel` (older than the field) is treated as the same channel. Otherwise it saves the tree and keeps the state lock, then starts the new ftmd in its own session with the listening socket (`FTMD_LISTEN_FD`) and a readiness pipe (`FTMD_READY_FD`). Both are removed from the environment before any thread starts. The new ftmd checks that the fd is a listening stream socket bound to its socket path and that the saved tree parses, then signals ready. The old one exits on that signal, still holding the lock, so none of its pane readers can save over the tree. The new ftmd waits to be reparented and then restores as after any restart. The socket stays bound and listening throughout: clients queue instead of finding nothing and starting a second ftmd. If the new ftmd exits, fails a check or is not ready within 15s, the old one kills it, releases the lock, carries on serving and sends `UpdateBlocked`. On macOS, holders spawned between the swap and the switch run the new binary; on Linux they run the old one through `/proc/self/exe`, since the replaced path reads as `(deleted)` there. On macOS, a new binary with the same frame version is harmless; with a different one the `Hello` check refuses them, the pane fails to open with an error the app shows, and the stray holder is killed. The app pings on each reconnect of its event stream and shows a notice while the daemon's version differs from its own.

An ftmd from before holders existed owns its PTYs directly, so stopping it ends its panes; both scripts detect that (panes without holder sockets) and ask first.

**Update check.** The app's `check_update` command (`app/src-tauri/src/update.rs`) runs about 10s after launch, every hour, after a settings change to `[updates]`, and from Settings → Updates → Check for updates. It goes through `curl` (unauthenticated, 60 requests an hour, so no new HTTP dependency). `[updates] check` decides whether the automatic checks run; unset, they run on every install but a debug build. The button passes `manual: true`, which checks whatever the setting says, and shows the result under it: the version this build counts as (`Checked.current`) and the time, the release on offer, or the error (the automatic checks only log errors). A release found by the button opens the dialog even if it was ignored or already shown. `[updates] channel` (unset: `paths::CHANNEL`, this build's) picks where to look. Stable reads `releases/latest` and takes it only if it is a published, non-pre-release semver with no pre-release part. Nightly reads `releases?per_page=10` (nightly.yml keeps 5) and takes the highest semver among published pre-releases tagged `-nightly.`, which skips an `-rc.1`. On the build's own channel only a newer version is offered. The other channel's newest is always offered, as a switch (`Update.switch`), whatever its version: the two are different packages, so this is a replacement rather than an upgrade.

`update::install` works out how this copy was installed (`Update.install`). A debug build is `dev`; a build made with `FTM_SOURCE_BUILD` set (`scripts/install.sh` sets it) is `source`. Otherwise it looks at `current_exe`. On Linux, under `/usr/bin`: `pacman -Qqo` naming `ftm-bin` or `ftm-nightly-bin` is `pacman`, `dpkg-query -S` naming `ftm` or `ftm-nightly` is `deb`, `rpm -qf` naming one of those is `rpm`. On macOS, the enclosing `FTM.app` or `FTM Nightly.app` is `brew` when `<prefix>/Caskroom/ftm` (or `ftm@nightly`) and `<prefix>/bin/brew` exist for `$HOMEBREW_PREFIX`, `/opt/homebrew` or `/usr/local`, and `mac_app` otherwise. Anything else is `unknown`. Each kind gets `how` (a sentence for the dialog), `commands` (to run by hand) and, where a package manager can do it from a pane, `script`. `pacman`, `deb`, `rpm` and `mac_app` need the release file for this machine (the `PKGBUILD`, the `_amd64.deb`/`_arm64.deb`, the `.x86_64.rpm`/`.aarch64.rpm`, the `_aarch64.dmg`/`_x64.dmg`, as release.yml and nightly.yml check for); a release without it yet (assets are attached after publishing) offers nothing until the next check. The downloading scripts `mktemp -d`, `curl` the file there and run `makepkg -si`, `sudo apt install ./<deb>` or `sudo dnf install ./<rpm>`; the dir is removed on success and kept on failure. None passes `--noconfirm` or `-y`. The pane is interactive anyway, and on a switch pacman asks "Remove ftm-bin?", which `--noconfirm` answers with its default, no, failing the install. The deb and rpm packages declare `conflicts`/`replaces` (`obsoletes`) on the other channel, so apt and dnf swap them. `brew` runs `brew upgrade --cask frazzer951/ftm/<cask>`, or on a switch installs (or upgrades, if present) the other channel's cask, which sits next to this one. `mac_app`, `source`, `dev` and `unknown` have no script.

`Update.prompt` is false for `source` and `dev`, which get a notice rather than the dialog. The dialog (`#release`) offers Update (Switch, with a warning that the new channel starts a fresh daemon and the open panes stay behind) when there is a script, else Download (the release file) or Open release, plus Release notes, Ignore this version and Later. Update spawns an "FTM <version> update" terminal ("FTM Nightly <version> switch" and the like) in `~` with the script as its `command`. After a switch, the old ftmd sees the other channel in `--handshake`, stays put and sends `UpdateBlocked`. It keeps the update pane and every other pane until it exits, and the new channel's app starts its own daemon. sudo can prompt in the pane, and the install then replaces `ftmd`, which triggers the self-upgrade above; the update pane's holder keeps running through it. Ignore stores the version in `localStorage` (`ftm.dismissedRelease`). Later, or Escape, closes the dialog and leaves a notice that reopens it. The app remembers the last release it brought up, so the hourly check stays quiet about it until the app restarts or the offer changes. If the daemon's version differs from the app's (an older ftmd would ignore `command` and open a bare shell), Update shows the commands to run by hand instead. To try the dialog from a dev build, `FTM_UPDATE_FAKE_VERSION=0.0.1` makes the check treat the app as that version and `FTM_UPDATE_FAKE_INSTALL` (`pacman`, `brew`, `mac_app`, `deb`, `rpm`, `source`, `dev` or `unknown`) as installed that way; either turns the check on in a debug build.

`Kind`, `Status` and `Event` each parse a value they do not know as `Unknown`, so an app still running against a newer ftmd (the usual state right after a self-upgrade) keeps reading its events; ftmd refuses `Unknown` in a request, so it never sends one. `SpawnRequest.command` needed no protocol or `frame::VERSION` bump. Frames are only spoken between ftmd and its holders, and the command reaches the holder as an environment variable at spawn. On the client socket, `command` is `#[serde(default)]` and serde ignores unknown fields, so an older ftmd reads a newer app's spawn as a plain terminal and an older client's spawn still parses. `claude_args` is the same, except that an older ftmd dropping it would quietly start a plain agent (with `--resume`, a new session instead of the one asked for). So `Pong` carries `features` (empty from an older ftmd), ftmd lists `claude_args` there, and `ftm spawn` pings first when it has extra arguments and refuses if the feature is missing. The field is left out of the request when empty, so a spawn without extra arguments is exactly what an older ftmd expects.
